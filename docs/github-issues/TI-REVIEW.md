# TI-REVIEW: ワークフローにレビューゲートが組み込まれていない

**ラベル:** `template`, `Critical`

---

## 背景

このテンプレートには、企画・設計の各フェーズをレビューするための Agent Teams が8チーム定義されています（`review-mrd`、`review-prd`、`review-model`、`review-specs` 等）。

## 問題

レビュー用の Agent Teams は定義されていますが、**ワークフロー（`.claude/rules/workflow.md`）のどのタイミングでレビューを実行すべきか**が記載されていません。レビューの実行は完全に任意であり、実行しなくても次のフェーズに進むことができます。

この結果、レビューが行われないまま設計が完了し、問題が後工程で大量に発見されるという事態が発生します。

## PG1 での事例

PG1 の設計過程では、企画から設計まで一気通貫で完了した時点では問題はゼロだと認識していました。その後、ユーザーの指示でレビューを実施したところ、4ラウンドにわたり合計33件の問題が発見されました。

| ラウンド | 実施内容 | 発見件数 |
|---------|----------|:-------:|
| 1 | 整合性レビュー（ユーザー指示で初めて実施） | 12件 |
| 2 | 4観点レビュー（エンジニア・デザイナー・API・ドメイン専門家） | 9件 |
| 3 | PRD 文献根拠の査読 | 8箇所 |
| 4 | KPT 振り返り + 統計計算の精密検証 | 4件 |

「ドキュメント変更時の影響範囲追跡の仕組みがない（TI-DEPS）」、「PRD の設計原則が抽象的なまま下流に渡る（TI-ABSTRACT）」、「LLM が生成した文献引用の正確性を検証する仕組みがない（TI-CITATION）」で報告されている問題はいずれも、**レビューゲートが設定されていれば早期に発見できたもの**です。

## 提案

ワークフローの各フェーズ完了後にレビューゲートを設け、通過条件を満たさない限り次のフェーズに進めない仕組みにします。

### レビューゲートの定義

```
MRD 完了    → review-mrd   → Pass → PRD へ
PRD 完了    → review-prd   → Pass → Conceptual Model へ
CM 完了     → review-model → Pass → Screens へ
Specs 完了  → review-specs → Pass → Impl Plan へ
実装完了    → review-code  → Pass → マージ
```

### 通過条件

- **Pass**: Critical が0件であること
- **条件付き Pass**: Critical が0件で、Warning 以下の指摘のみの場合は次フェーズと並行して修正可
- **Fail**: Critical が1件以上ある場合は修正完了後に再レビュー

### レビューチーム構成の指針

- **ドメイン専門家を含めること**を推奨します。PG1 では、メンタルヘルスの観点からのレビューが Strain 合成指標の構成誤りを発見しました。技術レビューだけでは気づけない問題があります
- `review-specs` は最低限「技術」「機能」「ドメイン」の3観点を含めることを推奨します

## 本 Issue の位置づけ

6件のテンプレート改善 Issue の中で最も優先度が高いものです。レビューゲートを導入することで、他の Issue で報告されている構造的問題を早期に検出できるようになります。

```
TI-REVIEW（レビューゲート）← 最初に導入する
    ├── TI-DEPS（依存追跡の漏れ）がレビューで検出可能になる
    ├── TI-ABSTRACT（抽象方針の未具体化）がレビューで検出可能になる
    └── TI-CITATION（文献引用の不正確さ）がレビューで検出可能になる
```
