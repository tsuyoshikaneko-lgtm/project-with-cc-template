# TI-ABSTRACT: PRD の設計原則が抽象的なまま下流に渡る

**ラベル:** `template`, `Critical`

---

## 背景

PRD の設計原則テーブルには「原則」「内容」「根拠」の3列があり、プロダクトの設計方針を定義します。この設計原則は下流の Specs（DB Schema、API Spec、UI Spec 等）の導出元として使われます。

## 問題

現在のテンプレート構造では、設計原則に**操作的定義（具体的な計算方法やアルゴリズム）**を記述する場所がありません。

「Strain と Recovery を独立2軸で表示する」のような抽象的な方針は書けますが、「どのメトリクスをどう合成するか」「その計算は統計的に妥当か」という具体化のステップが欠落しています。

この結果、抽象的な方針がそのまま下流に渡り、Specs 導出の段階で以下のような問題が発生します。

- 具体化できず、API にフィールドが定義されない
- 誤った具体化がされ、意図しない挙動になる
- ドキュメント間で解釈がずれる

## PG1 での再現事例（3回）

| 抽象的な設計原則 | 具体化の段階で発生した問題 |
|---|---|
| 「Strain/Recovery を独立2軸で表示する」 | 計算式が定義されなかった → API Spec にフィールドが作られなかった |
| 同上（計算式を追加した後） | Strain に Activity Score を含めた → 良い運動をした日が「高負荷」と誤判定される問題が発生 |
| 「Pearson 相関係数で30日閾値を設定する」 | 「検出力 50-60%」と記載したが、精密計算を行うと 44.5% であることが判明 |

## 提案

### 1. PRD の設計原則テーブルに「操作的定義」と「検証状態」の列を追加する

```markdown
| 原則 | 内容 | 根拠 | 操作的定義 | 検証状態 |
|---|---|---|---|---|
| Strain/Recovery | 独立2軸で表示 | RESTQ に着想 | Strain = stress の Z-score 単軸。Recovery = mood + energy + sleep_score + readiness_score + hrv_rmssd の Z-score 平均 | ドメインレビュー済み |
| 相関パターン | 30日閾値 | 検出力計算 | Pearson r ≥ 0.5 のペアを抽出。自己相関考慮で power = 50-62% | 検証済み: PG1 では許容 |
```

- **操作的定義**: 下流の Specs 導出に必要な具体的な計算方法・アルゴリズムを記述する
- **検証状態**: `未検証` / `検証済み` / `PG1では許容` など、判断の根拠の確からしさを明示する

### 2. Specs 導出後に API ↔ US 振る舞い照合を追加する

ユーザーストーリーが「〜を表示する」と記述している場合、API がそのデータを返却できるかを確認します。特に以下のエッジケースで矛盾が発生しやすいため、重点的に確認します。

- データが存在しない場合（メンタル未入力、フィジカル未取得）
- Oura 未接続の場合
- データ蓄積が不十分な場合（Z-score 計算に14日分必要）

### 3. 数値的主張には検証タグを付ける

PRD および Specs 内の数値的主張（効果量、検出力、閾値等）には `[検証済み]` / `[未検証]` のタグを付け、根拠の確からしさを明示します。

## 関連 Issue

- 「ドキュメント変更時の影響範囲追跡の仕組みがない（TI-DEPS）」: 抽象方針が具体化された際に下流への伝播を確実にする
- 「ワークフローにレビューゲートが組み込まれていない（TI-REVIEW）」: 抽象方針の妥当性をレビューで検証する
