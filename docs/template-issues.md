> このファイルは、同じ問題を踏まないためのテンプレート改善提案である。

**作成日**: 2026-03-19
**更新日**: 2026-03-22（v3: レビュー結果を反映して書き直し）

## 背景: 何が起きたか

設計フェーズを一通り完了した時点では、問題はゼロだと思っていた。

## Issue 1: 上流を変えても下流に伝播しない

> 上流ドキュメントを更新しても、下流のどこを直すべきかわからない。変更が伝播せずドキュメント間の整合性が壊れる。

**深刻度:** Critical（3回再発）
**影響:** `.claude/rules/workflow.md`

### 背景

ワークフローは `reqs → specs → 実装` の流れと、各 Spec の導出元を定めている。各 Spec ファイルにも `導出元` ヘッダーがある。

```
db-schema.md    ← product-model.json（entities）
api-spec.md     ← db-schema + conceptual-model + prd + user-stories
auth-spec.md    ← product-model.json（actors）+ prd
ui-spec.md      ← product-model.json（screens）+ prd + api-spec
test-spec.md    ← user-stories + db-schema + api-spec
impl-plan.md    ← user-stories + db-schema + api-spec + auth-spec
```

しかし導出元の記載は「初回作成時にどこを見るか」であり、**上流を更新したときに下流のどこを確認すべきか**（逆引き）が書かれていない。

### PG1 で3回発生した

| 何が起きたか | いつ |
|---|---|
| PRD で4軸を変更 → pg1.md が旧軸のまま残った | 3/19 |
| PRD に「睡眠ステージ比率」を明記 → DB Schema・API Spec・Test Spec すべてに `sleep_stages` がなかった | 3/19 |
| Auth Spec に「メール+パスワード認証」を定義 → DB の `users` テーブルに `email` も `password_hash` もなかった | 3/21 |

バージョン参照の陳腐化も同じ原因。現在の `impl-plan.md` は `auth-spec.md (v0.3)` を参照しているが、auth-spec は v0.4 に更新済み。

### 提案

**1. ドキュメント依存マップ**をワークフローに追加する（導出元の逆引き）。

| 更新したドキュメント | 確認が必要なドキュメント |
|---|---|
| pg{N}.md | prd.md |
| prd.md | pg{N}.md, conceptual-model.md, user-stories.md |
| conceptual-model.md / product-model.json | db-schema.md, api-spec.md, ui-spec.md |
| db-schema.md | api-spec.md, test-spec.md, impl-plan.md |
| api-spec.md | test-spec.md, impl-plan.md, ui-spec.md |
| auth-spec.md | db-schema.md, test-spec.md, impl-plan.md |
| user-stories.md | test-spec.md, impl-plan.md |

**2. フィールド照合チェック**を Specs 導出後に必須化する。

- PRD 機能概要の全データ項目 → DB Schema のカラムに存在するか
- DB Schema の全カラム → API Spec のレスポンスに存在するか
- API Spec の全エンドポイント → Test Spec にテストケースが存在するか
- Auth Spec の認証要件（例: メール+パスワード）→ DB Schema に対応カラムがあるか

**3. Spec ファイルの導出元にバージョンを書かない。** `impl-plan.md` の `導出元: auth-spec.md (v0.3)` のように固定バージョンを書くと陳腐化する。バージョンを書かず、常に最新を参照する運用にする。

## Issue 2: 抽象的な方針が計算式に落ちないまま下流に渡る

> PRDに抽象的な方針だけ書いて、計算式や構成要素を定義しないまま Specs に進める。下流で具体化できず設計が破綻する。

**深刻度:** Critical（3回再発）
**影響:** `.claude/rules/workflow.md`, `docs/reqs/prd.md`（テンプレート構造）

### 背景

PRD の設計原則テーブルには「原則」「内容」「根拠」の3列がある。

```
| 原則 | 内容 | 根拠 |
|---|---|---|
| Strain/Recovery | 独立2軸で表示 | RESTQ着想 |
```

しかし「独立2軸」が具体的に何を意味するか（どのメトリクスで構成するか、どう計算するか）を定義するステップがワークフローにない。抽象方針のまま Specs 導出に入ると、具体化できない・誤った具体化をする・ドキュメント間で解釈がズレる。

### PG1 で3回発生した

| 何が起きたか | いつ |
|---|---|
| 「Strain/Recovery 独立2軸」→ 計算式が未定義 → API Spec にフィールドが作られなかった | 3/19 |
| 計算式を追加 → Strain に Activity Score を含めたが「良い活動日=高負荷」と誤判定。API は日次時系列でなく集約値で返しグラフ描画不能。US の「空表示」と API の「404」が矛盾 | 3/21 |
| 「Pearson 相関の power 50-60%」で30日閾値設定 → 精密計算で 44.5% と判明 | 3/21 |

### 提案

**1. PRD の設計原則テーブルに「操作的定義」と「検証状態」列を追加する。**

```
| 原則 | 内容 | 根拠 | 操作的定義 | 検証状態 |
|---|---|---|---|---|
| Strain/Recovery | 独立2軸 | RESTQ着想 | Strain = stress の Z-score。Recovery = mood + energy + sleep_score + readiness_score + hrv_rmssd の Z-score 平均 | ドメインレビュー済み |
| 相関パターン | 30日閾値 | 検出力 | Pearson |r| >= 0.5。N=30 で power=44.5% | 検証済み: PG1では許容 |
```

操作的定義が空欄のまま Specs 導出に進むことを禁止する。

**2. API と US の振る舞い照合**を Specs 導出後に追加する。

US が「〜を表示する」と書いている場合、API がそのデータを返せるか確認する。特に以下のエッジケースで矛盾が起きやすい:
- 「データなし」の場合に US は「空状態を表示」だが API は 404 を返す
- 「未入力時に CTA を表示」だが API レスポンスに判定フラグがない

**3. 数値的主張にタグを付ける。** PRD 内の統計的数値には `[検証済み]` / `[未検証]` を必須化する。

## Issue 3: レビューチームが5つあるのにワークフローに組み込まれていない

> レビュー用 Agent Teams が5つ定義されているのに、ワークフローに実行タイミングが書かれていない。レビューなしで次フェーズに進めてしまう。

**深刻度:** Critical
**影響:** `.claude/rules/workflow.md`

### 背景

テンプレートには8つの Agent Teams が定義されており、うち5つがレビュー用（`review-mrd`、`review-prd`、`review-model`、`review-specs`、`review-code`）。各チームは「複数観点のレビューアーを並列に走らせ、指摘を集約して報告する」仕組みを持っている。

しかしワークフロー（`.claude/rules/workflow.md`）にはこれらのチームを実行するタイミングが一切記載されていない。レビューは完全に任意であり、実行しなくても次のフェーズに進める。

### PG1 での実例

企画から設計まで一気通貫で完了した時点では問題ゼロだと認識していた。その後ユーザーの指示でレビューを実施したところ、4ラウンドで合計33件の問題が見つかった。

Issue 1（依存追跡）・Issue 2（抽象→具体）・Issue 6（文献引用）の問題は、いずれもレビューゲートがあれば早期に発見できた。

### 提案

#### レビューゲートの配置

現在の `workflow.md` のフローに対応させる:

```
MRD 完了       → review-mrd   → Pass → PRD へ
PRD 完了       → review-prd   → Pass → Conceptual Model へ
CM 完了        → review-model → Pass → Screens へ
Screens 完了   → （※後述）    → Pass → Track A + B へ
Specs + Test   → review-specs → Pass → Impl Plan へ
Impl Plan 完了 → （※後述）    → Pass → 実装へ
実装完了       → review-code  → Pass → マージ
```

**※ Screens 完了後と Impl Plan 完了後にはレビューチームが未定義。** 対応方法は2つ:
- A: review-model の対象を Screens まで拡張する / review-specs の対象を Impl Plan まで拡張する
- B: 新しいレビューチームを作る

PG1 の経験では Screens 単体で問題が発生した事例はないため、まずは A（既存チームの対象拡張）で十分と考える。

#### 通過条件

現状、レビューチームの深刻度定義がバラバラ:

| チーム | 現在の深刻度レベル |
|--------|------------------|
| review-mrd | 最優先 / 高 / 中 / 低 |
| review-prd | 明示なし |
| review-model | 高 / 中 / 低 |
| review-specs | Blocker / Warning / Note |
| review-code | Critical / Warning / Suggestion |

**全チーム共通で以下に統一する:**

| レベル | 定義 | ゲートへの影響 |
|--------|------|--------------|
| Critical | このまま次フェーズに進むと手戻りが確定する | **Fail — 修正後に再レビュー** |
| Warning | 進行可能だが、放置すると問題化する | **条件付き Pass — 次フェーズと並行で修正** |
| Note | 現スコープでは許容。次回以降の検討事項 | Pass |

- **Pass**: Critical が 0 件
- **Fail**: Critical が 1 件以上 → 修正完了後に再レビュー

#### review-specs の既存ゲートとの関係

`review-specs.md` には既に「Review Gate」セクション（Specs が揃っているかの前提チェック）がある。これは**チーム内部の入力品質チェック**であり、本提案のゲートは**フェーズ間の遷移条件**。両者は補完関係にあり、矛盾しない。

#### レビューチーム構成の指針

- **ドメイン専門家を含めることを推奨する。** PG1 ではメンタルヘルスの観点からのレビューが Strain 合成指標の構成誤りを発見した。技術レビューだけでは気づけない問題がある
- 現在の review-specs は「技術」「機能」「統合」の3人構成でドメイン観点がない。ドメイン固有の設計判断を含む場合は、ドメインレビューアーの追加を検討する

## Issue 4: 並列と定義された Track A・B に実は依存関係がある

> ワークフローは Specs と Test Spec を並列で進めると定義しているが、Test Spec は API Spec を参照する。並列で書くと未完成の Spec を元にしてしまう。

**深刻度:** High
**影響:** `.claude/rules/workflow.md`

### 背景

ワークフローは Screens 完了後に2トラックを並列で進めると定義している:

```
Track A: Specs 導出（順次）— DB Schema → API Spec → Auth Spec → UI Spec → ...
Track B: User Stories → Test Spec
```

しかし `test-spec.md` のヘッダーに明記されている通り、Test Spec は Track A の成果物を参照する:

```
導出元: docs/reqs/user-stories.md, docs/specs/db-schema.md, docs/specs/api-spec.md
```

### PG1 での実例

- Test Spec が `GET daily_records` と書いたが、API Spec では `GET /api/v1/trends` だった
- Test Spec に「auth-spec 具体化後に更新する」というプレースホルダが残った

### 提案

Track B を「User Stories」と「Test Spec」に分離する:

```
Track A: Specs 導出（順次）— DB Schema → API Spec → Auth Spec → UI Spec → ...
Track B: User Stories（Track A と並列可）
Track C: Test Spec（Track A + Track B の両方が完了後）
```

User Stories は Specs と独立しているため並列で進められる。Test Spec は API Spec・Auth Spec・DB Schema への参照があるため、Track A 完了後に着手する。

現在のワークフローの「4. Impl Plan」のトリガー条件「Track A と Track B の両方が完了したとき」は、「Track A + B + C の完了」に変更する。

## Issue 5: デザインシステム外ライブラリの選定枠がない

> UI Spec テンプレートにデザインシステム外ライブラリ（グラフ、地図等）の選定セクションがない。必要なライブラリが選定漏れする。

**深刻度:** High
**影響:** `docs/specs/ui-spec.md`（テンプレート構造）

### 背景

UI Spec はデザインシステム（Material Web）を参照してコンポーネントを定義する。しかしデザインシステムにないUI要素（グラフ、地図、リッチエディタ等）のライブラリ選定セクションがテンプレートに存在しない。

### PG1 での実例

- トレンドダッシュボードにグラフが必要だったが、ライブラリが未選定のまま設計完了
- フィジカル（0-100スケール）とメンタル（1-7スケール）の Y軸スケール破綻が、ライブラリの具体的な設定を考える段階まで見落とされた

現在の `ui-spec.md` にはレビュー後に追加された「グラフライブラリ」セクションがあるが、これは PG1 固有の修正。次の PG で別種のUI要素が必要になった場合、同じ問題が再発する。

### 提案

UI Spec テンプレートの「デザインシステム」セクション直下に「外部ライブラリ依存」サブセクションを追加する:

```
### 外部ライブラリ依存

デザインシステムにないUI要素を使う場合、以下を記載する。
product-model.json の screens を確認し、該当する要素がある場合は記載必須。

| 用途 | ライブラリ | 選定理由 | バンドルサイズ | 依存パッケージ |
|------|----------|---------|-------------|-------------|
| （例: グラフ） | Chart.js | タップイベント対応、カラーゾーン帯 | ~65KB gzip | chart.js, chartjs-plugin-annotation |
```

このセクションが空欄の場合、product-model.json の screens に「デザインシステムでカバーできない要素がないか」を確認するステップを Specs 導出ワークフローに追加する。

## Issue 6: LLM が生成した文献引用・統計数値の正確性を検証するステップがない

> PRD に LLM が生成した文献引用があっても、正確性を検証するステップがワークフローにない。不正確な根拠がそのまま設計判断に使われる。

**深刻度:** High（2回再発）
**影響:** `.claude/rules/workflow.md`, `docs/reqs/prd.md`（テンプレート構造）

### 背景

PRD の設計原則テーブルには `根拠` 列があり、学術文献を引用する。この引用は LLM が生成するが、正確性を検証するステップがワークフローに存在しない。

### PG1 での実例

**文献引用の不正確（8箇所）:**

| LLM が書いた内容 | 実際 |
|---|---|
| 「VAS より脱落率が低い」(Haslbeck 2025) | コンプライアンスに有意差なし |
| 「EMA 疲労閾値15項目、5分」 | 出典なし（LLM の捏造） |
| Hedges' g = -0.776 を「集中」に帰属 | 「単純注意の失敗」が正しい帰属 (Lim & Dinges 2010) |
| 「主観ファースト」は実証済み | 設計仮説（実証未確認） |
| 「ウェアラブルは Z-score 正規化」 | 個人ベースラインは使うが Z-score とは限らない |

**統計数値の過大評価:**
- 「Pearson power 50-60%」→ 精密計算で 44.5%
- 「30日で十分」→ 自己相関考慮で power = 50-62%（不十分）

レビュー後、PRD は修正済み（「直接的相関は未検証だが」「設計仮説（実証未確認）」等の注記を追加）。しかしこれは PG1 固有の修正であり、次の PG で同じパターンが再発する仕組みの問題は残っている。

### 提案

**1. PRD の `根拠` 列に検証ステータスを追加する:**

```
| 原則 | 根拠 | 検証 |
|---|---|---|
| トレンド重視 | Baron et al. 2017 | 査読済み |
| 最小入力 | Wrzus & Neubauer 2023 | 査読済み |
| 主観ファースト | Orthosomnia 文献からの翻訳 | 設計仮説（未実証） |
```

検証ステータスは3種: `査読済み` / `設計仮説` / `未検証`。`未検証` の根拠に基づく設計判断は、その旨を下流ドキュメントに明記する。

**2. review-prd のレビュー観点に文献査読を追加する。** Issue 3 のレビューゲートで review-prd が必須実行されるようになった場合、レビューアーの観点に以下を追加する:
- 引用文献の主張が原典の内容と一致しているか
- 効果量・検出力などの数値が正しいか
- 「実証済み」と書かれているものが本当に実証されているか

## 対応の優先順位

```
Issue 3（レビューゲート）← 最初に導入する。他の全 Issue の早期検出に効く
    │
    ├── Issue 1（依存追跡）がレビューで検出可能になる
    ├── Issue 2（抽象→具体）がレビューで検出可能になる
    ├── Issue 4（並列トラック依存）がレビューで検出可能になる
    ├── Issue 5（UIライブラリ選定漏れ）がレビューで検出可能になる
    └── Issue 6（文献引用の不正確さ）がレビューで検出可能になる
```

レビューゲートは他の Issue の**根本対策ではなく早期検出策**。各 Issue の構造的な修正（依存マップ、操作的定義の必須化、トラック分離、テンプレートセクション追加、文献検証ステップ）は別途対応が必要。

推奨順序: Issue 3 → Issue 1 → Issue 2 → Issue 6 → Issue 4 → Issue 5
